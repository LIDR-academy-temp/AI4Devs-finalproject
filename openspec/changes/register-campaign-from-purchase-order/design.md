## Context

See `proposal.md` — Why. This is the first change in the project: there is no `backend/`, `frontend/` or `nginx/` directory yet, only `docker-compose.yml` and `.env.example`. The schema this change creates is therefore the initial schema, and its shape constrains everything built afterwards.

The data model is specified in `readme.md` §3. The constraint that drives most decisions here is that the economic rules must be testable without a database, an HTTP server or a DSP, because a wrong number in a margin is invisible until someone reconciles a year of data.

## Goals / Non-Goals

**Goals**

- An initial schema that the delivery and margin changes can build on without restructuring it.
- Validation that fails at the boundary with a message naming the offending value, not a stack trace.
- Adform reachable behind an interface, so phase 2 adds Equativ and Displayce without touching the registration service.

**Non-Goals**

- Performance work on the delivery table. It is created by `daily-campaign-delivery-status`, where its volume is the design problem.
- A rate-card or pricing engine. Sale CPM is entered, not derived.

## Decisions

**Periods are generated server-side, not supplied by the client.** The monthly expansion is a domain rule — one period per calendar month, clipped to the campaign dates — so it lives in the domain layer and is exercised by unit tests with no database. The alternative, letting the client post the periods, would put a business rule in the browser and allow a campaign whose periods do not tile its date range.

**`scope` is a database-level enumerated value; `market_description` is free text.** The alternative considered was keeping one `location` field and classifying it at read time. Rejected because that is exactly what the current Qlik script does, and 2% of its values classify into neither bucket. Making scope a required, validated field moves the failure from a silently averaged rate to a rejected form.

**Contracted volume and sale CPM sit on `campaign_lines`, with a nullable FK to `purchase_order_versions`.** `readme.md` §3 records this as the point where the domain model is ambiguous — the alternative is a bridge table carrying volume per line per version. Chosen because 62% of current campaigns have no purchase order at all, so the values must be able to exist without a version; the version FK records which order put them there when one exists. A revision creates new line rows against the new version, preserving the superseded ones.

**The Adform client implements a narrow interface with one method for this change: resolve an external identifier.** The ingestion methods arrive with the delivery change. The registration service depends on the interface, so its tests use an in-memory double and never reach the network.

**Validation failure and DSP unreachability are distinct outcomes.** An unknown identifier is a rejected request; an unreachable API is a failure the user can retry. Collapsing them would let an outage look like bad data entry and teach operators to re-type correct identifiers.

**Monetary and rate columns are `Numeric`; Python uses `Decimal`.** Rebate rates are applied to revenue and accumulate across a year, so float drift surfaces during reconciliation.

## Risks / Trade-offs

- **The agency master is a migration prerequisite, and 22 values do not resolve.** → Reconciliation by Operations is a task in this change, not a follow-up. The historical load is blocked on it, which is the intended pressure.
- **Adform validation on save adds a network call to the form submit.** → Roughly 30 seconds per line by the PO's estimate, accepted deliberately: it is the mitigation for the highest risk in the project. A slow or failing call degrades to an explicit retry, never to an unvalidated save.
- **Choosing line-versioning over a bridge table may prove wrong** if a revision turns out to change only some lines. → The FK is nullable and the decision is recorded in `readme.md` §3.3 as pending validation; reversing it is an additive migration, not a rewrite.
- **The first schema is the hardest to change later.** → Alembic from the first migration, with no hand-edited schema and every autogenerated migration reviewed, since Alembic detects a rename as a drop plus an add.

## Migration Plan

1. Alembic initialised; first migration creates identity tables (`users`, `roles`, `user_roles`), masters, the campaign tree, purchase orders and `dsp_mappings`.
2. Master seed imported from `campaigns.xlsx` (`Customer` sheet for the group/agency hierarchy, `trading` for the DSP catalogue) and `extraprimas 2026.xlsx` for the holding groups.
3. Collisions reported: near-duplicate names differing by accent or separator, and the 22 unresolved agency values. Operations reconciles before anything else loads.
4. Rollback is `alembic downgrade`; no data exists in production at this point, so the destructive path is acceptable here and will not be later.

## Open Questions

- Whether the campaign lifecycle needs states beyond active and inactive, and what they are. It does not change this schema: a status column exists and its value set can be constrained later without restructuring.
