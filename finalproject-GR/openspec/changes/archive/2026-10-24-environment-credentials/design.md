# Design

## Context

See proposal.md - Why. `secrets-encryption` (archived) already provides `encrypt(prisma, workspaceId, secretId, plaintext)` / `decrypt(prisma, workspaceId, secretId, ciphertext)`, bound to a workspace and a secret's own id as AAD — this change is their first real caller. `test-case-authoring`/`test-case-delete` (archived) are the closest precedent for a project-scoped tenant table with full CRUD plus role-gated mutation: `test_case` is created/listed/updated by Contributor+, deleted by Admin+, nested under `/projects/:projectId/...` so `ProjectRoleGuard` + `resolveProjectWorkspaceId` resolve workspace scope without a new RLS shape. `ActivityLogger.log(tx, …)` exists (from `activity-log`) but has never actually been called from a controller yet — this change is also its first real caller.

PRD §6.7 states Project Settings (which includes the Environments section) is "Accessible to Project Admins and Workspace Owners only," while PRD §6.3.3/§6.4's "Handling of stored secrets" bullet and ADR 0004's own context table both state the *reveal* action itself is available to "Contributors and Admins" — the PRD's narrower phrasing there is about who can reach the environment-editor *screen*, read in context: "Admins in the environment editor; Contributors and Admins in the environment panel of an execution." That execution panel is Phase 6, not built yet. Resolved below rather than left open, since it fixes this change's role gates.

## Goals / Non-Goals

**Goals:**
- Environment CRUD (name, base URL, default browser) and credential management (alias, email, password) as one project-scoped resource, following the existing `test_case` controller shape.
- The reveal endpoint exactly as ADR 0004 #5 specifies: Contributor-or-Admin authorization, same-transaction audit log entry, rate-limited, `Cache-Control: no-store`.
- Wire `ActivityLogger.log` into a controller for the first time, in the same transaction as the reveal's decryption.

**Non-Goals:**
- The New Execution modal's environment picker and the execution-detail environment panel (PRD §6.3.3) — Phase 6, not started. This change's reveal endpoint is written so that panel can call it unchanged later; no rework anticipated.
- G10 (what happens to a Draft/Ready execution's environment link when that environment is deleted) — no `test_execution` table exists yet, so there is nothing to clear. Stays open for Phase 6.
- Re-masking the reveal UI after an interval (open-questions.md C2) — frontend concern; this slice, like Phase 5 Slice 1, is backend-only per roadmap-mvp.md's sequencing note.
- A KMS-backed `KeyProvider`, master-key rotation — already out of scope per `secrets-encryption`'s own design.md; unchanged here.

## Decisions

**Role gates: read and reveal are Contributor/Viewer-reachable; only create/update/delete are Admin-gated.** Resolving the PRD/ADR tension above: `GET` (list, detail — alias and email, never password) is `Viewer`+, matching PRD §6.3.3's explicit statement that Viewers see alias and email. `POST`/`PATCH`/`DELETE` on the environment itself are `Admin`+, matching PRD §6.7's Project-Settings-level restriction on configuration changes. `reveal` is `Contributor`+, matching ADR 0004 #5 and its context table verbatim ("authorises Contributor or Admin") rather than the stricter "Admins in the environment editor" phrasing, which describes today's only built screen, not a hard ceiling on the action. This means a Contributor can call `GET`/`reveal` today with no UI reason to (no execution screen exists yet) and that's fine — it's the same endpoint Phase 6's execution panel will call, so nothing here needs loosening later.

**Credentials are managed as part of their parent environment, not a separate resource.** PRD §6.7 shows one environment-editor modal covering name, base URL, default browser, and all of its credentials together. `PATCH /environments/:id` accepts a full `credentials` array (each with `alias`, `email`, and optionally a new `password`) and reconciles it against existing rows (update by id, insert new aliases, delete removed ones) inside one transaction — mirroring how the New Execution modal (PRD §7.2) and environment editor are both single-form UIs, not multi-step wizards. A credential's `password` field is write-only: omitting it on a `PATCH` leaves the stored password unchanged; an empty string is rejected (a credential must have a password to be revealable), matching `test_case`'s `PATCH` pattern of "omitted means unchanged" for `gherkinScript`.

**`secretId` for `encrypt`/`decrypt` is the credential row's own id**, generated before the insert (`gen_random_uuid()` default, read back via `RETURNING`, or pre-generated in the application and passed into the `INSERT` — either works; tasks.md picks pre-generating in the application so the same id is available for the encrypt call and the insert in one pass). This matches `secrets-encryption`'s binding model exactly — a credential's ciphertext fails to decrypt if copied to a different credential row, even within the same environment or workspace.

**No new mechanism module, no new ESLint allow-list entry.** The environments controller calls `encrypt`/`decrypt` (already public, already callable by any module — only `PrismaClient` *construction* is restricted, not these functions) through the ordinary `PrismaService` + `withTenantContext` path every other controller uses. Nothing here needs direct `PrismaClient` access.

**Rate limiting the reveal endpoint: an in-process fixed-window counter, no new dependency.** No queue, no Redis exists in v1 (ADR 0001/0005), and the API runs as a single Node process in local dev and in the only deployment target decided so far — so a `Map<userId, { windowStart, count }>` inside a small guard/interceptor is sufficient, consistent with `secrets-encryption`'s own precedent of reaching for Node's built-in `crypto` over a new package rather than installing `@nestjs/throttler` for one endpoint. Limit: 10 reveals per user per 60-second window (generous enough for legitimate re-checking during test setup, tight enough to blunt a brute-force credential-enumeration attempt). A rejected attempt throws `429 Too Many Requests` and is itself **not** logged to the activity log (only successful reveals are audited, per the spec's rolled-back-reveal scenario). **Revisit trigger:** replace with a persistent/distributed limiter (e.g., a Postgres-backed counter) the moment the API runs as more than one process — an in-memory counter is per-instance and silently resets on restart, which is acceptable for a single-instance v1 but not beyond it.

**Reveal's "same transaction" is read-decrypt-then-log, not one literal DB transaction.** `secrets-encryption`'s `decrypt(prisma, workspaceId, secretId, ciphertext)` manages its own `withTenantContext` transaction internally and cannot be nested inside a caller's transaction (its signature takes a bare `PrismaClient`, not a `Prisma.TransactionClient` — unchanged, since this change doesn't modify that capability). The reveal handler therefore: (1) reads the credential's ciphertext in one `withTenantContext` transaction, (2) calls `decrypt` — a second, separate transaction internally — and (3) only on success, opens a third `withTenantContext` transaction to write the activity-log entry. This still satisfies ADR 0004 #5's actual intent and this change's spec scenarios exactly: a decrypt failure (steps 1–2) never reaches step 3, so no audit entry is ever written for a reveal that didn't succeed, and a successful reveal always produces exactly one entry.

**Activity log entry shape for a reveal:** `category: 'Environments'` (PRD §6.6 already lists "Environments" as one of the Activity filter pills), `actionCode: 'environment_credential.revealed'`, `entityType: 'environment_credential'`, `entityId` the credential's id, `entityName` the credential's alias (so the log reads sensibly even if the credential is later deleted, per `activity-log`'s no-foreign-keys requirement), and `details: { environmentId, environmentName }` so the entry can show which environment the credential belonged to without a join.

**Migration file:** `db/migrations/0007_environment_credentials.up.sql`/`.down.sql`, next in sequence after `0006_secrets_encryption`.

## Risks / Trade-offs

- [In-memory rate limiter resets on process restart and doesn't coordinate across instances] → Accepted for v1 single-process deployment; revisit trigger recorded above, same posture ADR 0004 already takes toward deferring KMS.
- [`PATCH` reconciling a `credentials` array by alias/id is more complex than a flat field update] → Matches the PRD's actual UI (one modal, one save), and reconciliation logic is small (diff by id, insert new, delete missing) — not worth splitting into a separate credentials sub-resource for this slice.
- [Allowing `Contributor`+ to call `GET`/`reveal` today when no UI exposes that to Contributors yet] → Deliberate: avoids a second role-gate change when Phase 6 builds the execution panel that needs exactly this access level.
