# ADR 0006: Report Generation

**Status:** Accepted
**Date:** 2026-09-23
**Amends:** [ADR 0001](0001-tech-stack.md) (adds a layer ADR 0001 named only as "report generation workers")

## Context

[PRD.md](../../PRD.md) §8 requires six downloadable reports:

| Report | Requirement |
|---|---|
| Execution HTML | A standalone file with images embedded, viewable with no internet connection |
| Execution PDF | Same data, print-ready |
| Overview, Test Cases, Executions and Bugs dashboards (PDF) | Charts that should match what users see on screen |

Constraints already fixed by earlier ADRs and the PRD:

- Reports run as background jobs (ADR 0005) under the tenant context (ADR 0003).
- Reports never contain stored credentials, tokens or keys (PRD §8, ADR 0004), and items in the trash are excluded (PRD §2.11).
- Bug images are up to 5 per bug and 5 MB each, in JPEG, PNG, WebP or GIF (PRD §7.3), so an execution with many bugs can produce very large files.
- The PRD offers Japanese and Portuguese locales (§7.2), so report text may include non-Latin scripts.

## Decision

**Reports are generated by the worker from one assembled data object. The HTML export comes from a server-side HTML template, and PDFs come from a PDF library (pdfmake by default) with no headless browser.**

1. **One data-assembly step.** A single function per report builds a plain, allow-listed report data object under the tenant context. It contains no secret fields and no trashed items. Both output paths consume only this object.
2. **HTML export.** A server-side template renders the data object to one standalone file: inline CSS, images embedded as base64, charts as inline SVG, no scripts and no external requests. All user-provided text is escaped.
3. **PDF export.** The same data object is turned into a pdfmake document definition. The library does not interpret HTML, so user text is data by construction.
4. **Charts are drawn once.** A shared chart module turns a chart specification (series, colours, thresholds) into a static SVG string. That string is embedded in the HTML export and passed to pdfmake as an `svg` node, which the library accepts directly. The interactive charts in the web app use the UI's own chart library, but chart specifications live in a shared package to limit visual drift.
5. **Images.** Originals are never altered. Each image is converted and resized for the report (JPEG or PNG, with a maximum dimension, default 1600 px), processed one at a time so memory stays bounded. A total-size cap fails the job with a clear message instead of exhausting memory.
6. **Delivery.** Generation is a job. When it finishes, the file is stored in object storage and the user is notified over the SSE channel with a short-lived signed download link.
7. **Limits.** Each worker runs a small number of report jobs concurrently, with a timeout. Jobs are idempotent and retried with backoff.

## Rationale

- **Light worker.** No Chromium means the worker runs in any small Node container without a browser dependency or the memory a browser needs, and there is no browser attack surface in the worker.
- **Shared data, shared charts.** Assembling the data once keeps secrets and trash rules in one place and makes it hard for one output to leak something the other omits. Drawing charts once as SVG means the largest visual component is not implemented twice.
- **Escaping by construction.** The PDF path never parses markup from user content.

## Alternatives Considered

- **Headless Chromium in the worker (recommended by the initial analysis).** One HTML template would drive both exports with pixel-faithful charts and system font fallback for any script, and Playwright is already on the roadmap. Not chosen for v1 in favour of a lighter worker. This is the main alternative to revisit (see triggers).
- **react-pdf.** Similar model to pdfmake with React components. Not chosen as the default because the documentation reviewed lists only its own SVG primitives and does not confirm rendering an existing SVG string.
- **Managed rendering API (Browserless, DocRaptor).** Rejected: every render has a cost and customer test data would leave our infrastructure.
- **A separate rendering service (Gotenberg).** Not chosen; it would add a service to operate.
- **Client-side printing.** Rejected: cannot run as a background job, produces inconsistent output, and cannot build the self-contained HTML file.

## Consequences

- **Two layouts to maintain.** The HTML template and the PDF document definition must both be updated when a report's design changes. Sharing the data object and the chart module contains the cost but does not remove it.
- **Font coverage is a real risk.** PDF libraries embed fonts explicitly and do not fall back to system fonts. Default fonts lack Japanese and other scripts, so a font strategy is required (embedding a Noto family with the needed coverage, with the file-size cost that brings). Text in a script that is not covered would render as missing glyphs.
- **SVG fidelity limits.** pdfmake converts SVG through another library that may not support every SVG feature. Charts must be authored within a tested feature subset.
- Reports are asynchronous, so the UI needs a "generating" state and a ready notification.
- Report files and their signed links need a retention rule.

## Revisit Triggers

- Non-Latin text or chart rendering fails in real reports.
- Users report that PDFs look materially different from the app, or the two templates drift repeatedly.
- **The automated execution engine ships.** Chromium then becomes a dependency anyway, and a browser-based renderer becomes nearly free to add.

## Open Items

- A short spike before implementation: chart fidelity through the SVG path, font coverage including Japanese, and PDF generation time for a large execution.
- Image size cap, maximum report size, and the resize dimension.
- Retention period for generated report files and lifetime of the signed download link.
- Final library choice (pdfmake or react-pdf), settled by the spike.
